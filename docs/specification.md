# Спецификация «Маршрутизатор 3.0»

> Документ Этапа 3. Формализует входные/выходные файлы, правила валидации,
> нормализации, цикличности, ограничения, ошибки и критерии приёмки. Ссылается
> на решения R1–R7 из `architecture.md` (§10).

## 1. Область

Веб-приложение: пользователь загружает базу планирования и шаблон маршрутного
листа, система возвращает заполненный маршрутный лист на месяц.

## 2. Входной файл №1 — база планирования (`.xlsx`)

Обязательные столбцы (порядок не важен, но имена должны совпадать):

`Единый код`, `Старый код`, `Статус`, `Населенный пункт`, `Тип улицы`,
`Название улицы`, `Номер дома`, `Номер строения`, `Номер корпуса`,
`Станция метро`, `Дополнительное описание месторасположения точки`, `Партнер`,
`Субдилер`, `Субканал`, `Код Супервайзера`, `Код торгового представителя`,
`Цикличность`.

## 3. Входной файл №2 — шаблон маршрутного листа (`.xlsx`)

Столбцы результата (система заполняет значения, структуру не придумывает):

`№ п/п`, `Дата визита`, `День недели`, `Единый код`, `Старый код`, `Статус`,
`Населенный пункт`, `Тип улицы`, `Название улицы`, `Номер дома`,
`Номер строения`, `Номер корпуса`, `Станция метро`,
`Дополнительное описание месторасположения точки`, `Партнер`, `Субдилер`,
`Субканал`, `Код Супервайзера`, `Код торгового представителя`,
`Сколько раз посещаем в месяц`.

Соответствие: `Сколько раз посещаем в месяц` = `Цикличность` точки.

## 4. Правила валидации

| # | Проверка | Поведение при ошибке |
|---|---|---|
| V1 | Оба файла загружены | `FILE_ERROR` «Не загружен файл базы планирования» |
| V2 | Расширение `.xlsx` | `FILE_ERROR` «Поддерживается только формат .xlsx» |
| V3 | Все обязательные столбцы присутствуют | `VALIDATION_ERROR` «Отсутствует обязательный столбец: {имя}» |
| V4 | Нет пустых критических значений (`Единый код`, `Название улицы`, `Цикличность`) | `VALIDATION_ERROR` с указанием строки и столбца |
| V5 | `Цикличность` — целое ≥ 1 и ≤ числа рабочих дней | `VALIDATION_ERROR` «Некорректная цикличность в строке {n}» |
| V6 | `Единый код` уникален | `VALIDATION_ERROR` «Дублирующийся Единый код: {код}» |
| V7 | Адресные данные корректны (улица не пуста, есть населённый пункт) | `VALIDATION_ERROR` |
| V8 | Структура шаблона содержит все столбцы результата | `VALIDATION_ERROR` |

Ошибки формулируются для обычного пользователя (раздел 12 ТЗ), с кодом машины
в поле `code` (см. `architecture.md` §7).

## 5. Нормализация адресов

Нормализация применяется **только внутри алгоритма** (A9), исходные значения
экспортируются без изменений. Правила:

- регистр → нижний;
- сокращения типов улиц: `ул.` / `улица` / `УЛ` → канонический токен `ul`;
- удаление точек, лишних пробелов;
- нормализация дефисов и номеров домов/корпусов/строений;
- склейка в канонический ключ: `locality | metro | street | house | building`.

`ул. Ленина`, `улица Ленина`, `УЛ ЛЕНИНА` → один канонический ключ.

## 6. Геокодирование

- Внутреннее представление точки: `Geopoint` с `latitude`/`longitude`
  (опционально) и `normalized_address`.
- Координаты в базе отсутствуют (R1). Если геокодер недоступен — используется
  кластеризация по каноническому адресу.
- Геокодер за интерфейсом `Geocoder`; провайдер — Яндекс (R1, ключ в `.env`).

## 7. Цикличность и визиты

- `Цикличность = f` → ровно `f` визитов точки (раздел 5 ТЗ).
- Каждая точка с `f` создаёт `f` слотов `(point_id, slot_index)`, где
  `slot_index = 0..f-1`.
- Повторные визиты распределяются по месяцу максимально равномерно
  (приоритет №3): `4` визита → примерно неделя 1/2/3/4, не подряд.
- Общее число визитов = сумма `f` по всем точкам.
- Если `f > число рабочих дней`, визиты укладываются «сколько влезает»
  (по одному на день), пользователю показывается предупреждение (R5).

## 8. Рабочие дни и календарь

- Работа в выходные запрещена (R4): рабочие дни — Пн–Пт.
- Праздники и индивидуальные графики — через `CalendarProvider` (будущее).
- Период задаётся `period_start`/`period_end` (A5); число рабочих дней
  вычисляется по календарю.

## 9. Ограничения распределения

| Параметр | Значение | Тип |
|---|---|---|
| `min_points_per_day` | 15 (дефолт) | мягкое целевое (R3) |
| `max_points_per_day` | 25 (дефолт) | мягкое целевое (R3) |
| целевая нагрузка | `total_visits / working_days` | целевое |
| цикличность | строгая | жёсткое |
| рабочие дни | только допустимые | жёсткое |

При конфликте ограничений с цикличностью приоритет у цикличности (R3).

Приоритеты оптимизации (раздел 8 ТЗ), в порядке убывания:
1. корректность (все точки, точное число визитов, нет лишних/потерянных);
2. географическая компактность;
3. равномерность цикличности;
4. равномерность нагрузки по дням;
5. логичный порядок внутри дня.

## 10. Выходной файл

- Шаблон копируется с сохранением стилей/форматирования; строки заполняются
  по всем столбцам результата (R6).
- `№ п/п` — сквозная нумерация; `Дата визита` — дата дня; `День недели` — имя.
- Исходные значения точки переносятся без искажений (A9).
- `Сколько раз посещаем в месяц` = цикличность точки.

## 11. Состояния интерфейса (раздел 28 ТЗ)

`до загрузки` → `загружен первый файл` → `загружены оба файла` (активна кнопка
«Упорядочь хаос») → `обработка` (тексты: «Анализируем базу…», «Группируем
точки…», «Строим маршруты…», «Проверяем цикличность…», «Формируем маршрутный
лист…») → `успех` («Маршрут готов!» + кнопка «Скачать маршрутный лист») →
`ошибка` (понятная причина).

После успешного завершения дополнительно показывается карта с маршрутами по
дням (выбор дня, цветовая раскраска) — R7.

Стиль: minimal/modern, градиент фиолетовый → teal/морская волна → неон.

## 12. Критерии приёмки (раздел 39 ТЗ)

1. Загружаются оба Excel-файла.
2. Структура файлов корректно проверяется.
3. Данные корректно читаются.
4. Учитываются все точки базы.
5. Цикличность каждой точки соблюдена.
6. Нет лишних посещений.
7. Нет пропущенных посещений.
8. Визиты только на допустимые рабочие дни.
9. Нагрузка по дням максимально равномерна.
10. Географически близкие точки по возможности в одном маршруте.
11. Внутри дня — логичный порядок.
12. Результат проходит автопроверку.
13. Формируется корректный Excel.
14. Исходные данные не искажены.
15. Пользователь может скачать маршрутный лист.

## 13. Нефункциональные требования

- **Корректность** важнее скорости (приоритет №1).
- **Производительность:** 600 визитов / 300 точек обрабатываются за секунды;
  «большая база» (Тест №5) — за разумное время (< 10 с без учёта геокодирования).
- **Тестируемость:** ядро без I/O, детерминированные сиды, воспроизводимость.
- **Расширяемость:** веса факторов, метрика, солверы — настраиваемы (раздел 34).

## 14. Согласованные дополнения

- **Несколько сотрудников (R2):** база разбивается по `Код торгового
  представителя`; маршрутный лист строится для каждого кода.
- **Карта маршрутов (R7):** `GET /api/result/{job_id}/geojson` возвращает
  маршруты по дням (GeoJSON); frontend показывает их на карте (Leaflet/OSM).
- **Геокодер (R1):** Яндекс, ключ из `.env` (`GEOCODER_PROVIDER=yandex`).
